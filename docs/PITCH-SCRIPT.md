- **Total target runtime:** ~2:45–2:50. Write buffer is intentional — a live demo that lingers 5–10s still lands inside 3:00.
- **Pacing rule:** Slow down on the demo narration and on the ~40-second metric. Let the on-screen action breathe. Everything else can be crisp.

- **Live crash safety net:** A pre-recorded flawless fallback run is queued. If the live demo dies, cut to the recording mid-narration — the script works identically over the recording.
- **Single presenter assumed.** If pitching as a pair, the natural hand-off seam is at 2:00 — one presenter owns the hook + demo narration; the second takes proof/impact through the close.

## JUDGE Q&A OBJECTION BANK (14 Questions)

---

### 1. "Is the refund real?"

When keys are connected, it's a real Stripe TEST-mode refund object — a genuine API call that returns a Stripe refund ID. When keys aren't present, the dashboard clearly labels it a simulated refund (`re_sim_*`) and we never hide which mode we're in. The agent really decides and calls the action — the live-or-simulated distinction is about credentials, not about the agent doing the work.

---

### 2. "Did you just clone a template or a BimpeAI demo?"

No. We built the orchestration layer: the agent's decision logic, the Stripe refund action call, the parallel email and WhatsApp confirmation fan-out, and the live SSE dashboard that makes the whole thing visible in real time. BimpeAI is the conversation and action substrate — the trusted-to-act, confirm-across-channels flow is ours.

---

### 3. "What's novel versus a chatbot?"

A chatbot answers; this agent acts — it moves real money and proves it across two channels, without a human in the loop. "Chatbots answer. Action Agents act." That's the category wedge: no FAQ bot is trusted to call Stripe.

---

### 4. "Does it scale? Is it deployable?"

Deployable tomorrow on documented primitives — BimpeAI, Stripe, email, WhatsApp. The architecture (Next.js BFF, server-side secrets, SSE, mode-flagged fallbacks) is the same shape you'd ship. We'll be honest: we demo one customer and one order; productionising adds volume guardrails and a real datastore — that's an engineering sprint, not a rethink.

---

### 5. "What about fraud or abuse of auto-refunds?"

Refunds run inside a policy envelope: the agent checks the order and customer match, the return window, and a value ceiling before acting. Every action is logged and confirmed across two channels, which is itself an abuse signal — anomalous patterns surface immediately. Higher-risk cases escalate to a human. It auto-acts within a policy, it doesn't act unconditionally.

---

### 6. "(BimpeAI judge) Could you build the other use cases?"

Yes — they're already planned as published BimpeAI recipes riding the same primitives: Subscription Saver (recover MRR from a cancellation), Pay-to-Book (take a deposit, lock a slot), Invoice Reminder (chase a payment). Each is a recipe swap, not new infrastructure — that's the whole platform bet.

---

### 7. "How is this different from Zendesk, Gorgias, or Intercom AI?"

Those tools route tickets and surface suggestions for a human agent to act on. This agent acts — it calls Stripe, it sends the confirmation, it closes the loop. The distinction isn't speed; it's autonomy. They hand off to a human; this doesn't.

---

### 8. "How do you make money? What's the business model?"

SME SaaS — per-agent or per-action pricing. The insight is that every high-value SME customer conversation has the same shape: decide, transact, confirm. We charge for the value in that action, not just for the chat window.

---

### 9. "Why BimpeAI and not build it raw?"

BimpeAI wires conversation to Stripe to WhatsApp with a dashboard in an afternoon — it gave us the substrate so we could spend the hackathon on the orchestration that matters. Speed to market is the point; we're not married to any layer we'd need to swap.

---

### 10. "What was the hardest part to build?"

The trusted webhook-to-bus-to-SSE path: catching the real Stripe refund event, validating it, and fanning out two confirmations — email and WhatsApp — that look identical whether the system is live or in fallback mode. Getting that to be crash-proof on stage was the hard bit.

---

### 11. "What breaks at 100×?"

Three known things: per-merchant rate limits on the confirmation channels, WhatsApp template approvals (required at volume), and in-memory order state that needs a real datastore. None of these are architectural surprises — they're known, bounded problems, not reasons to rethink the design.

---

### 12. "What would you do with another week?"

Turn on voice (one-click on BimpeAI), wire a real merchant order API to replace the seed data, and ship Subscription Saver as the second published recipe to prove the platform generalises.

---

### 13. "Why should a customer trust an agent with their money?"

Because confirmation is the default, not an afterthought — every action the agent takes is proven across two channels, email and WhatsApp, immediately. The customer sees proof; the merchant has a log. Trust to act and prove it is the whole category proposition.

---

### 14. "You built this in one night — is it real or just smoke and mirrors?"

The golden path is real: real agent decision logic, a real Stripe API call in TEST mode, real email and WhatsApp dispatch, and a live SSE event stream on the dashboard. What's scoped is the breadth — one order, one customer, one happy path. The architecture is the same shape you'd ship; the scope is honest hackathon scope.
